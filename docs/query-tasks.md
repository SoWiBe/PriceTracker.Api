# PriceTracker: задачи по запросам (только описания, без SQL)

Для каждой задачи ниже сказано, что должен вернуть запрос и на какие ловушки смотреть.
SQL пишешь ты. Когда запрос готов: сначала прогони его в SQL-клиенте, потом оберни в Dapper,
потом сними `EXPLAIN (ANALYZE, BUFFERS)` и положи план в `docs/queries.md`.

Эндпоинты 1–7 взяты из CLAUDE.md. Эндпоинты 8–15 — реконструкция: оригинальный список из 15
потерян. Замени их, если найдёшь исходный чат.

Тестовые данные из seed:
- Ноутбук: 3 изменения цены.
- Наушники: 3 изменения, последнее запланировано на будущее.
- Клавиатура: 1 изменение, удобно проверять точное совпадение даты.
- Монитор: истории цен нет вообще.
- Мышь: цена прыгает вверх и вниз, годится для отчётов.

## Часть 1. Текущий код: что исправить в первую очередь

1. **GET товара по id, пропущен `await`.** Вызов репозитория не ожидается, поэтому проверка
   по шаблону всегда истинна: эндпоинт никогда не вернёт 404 и сериализует Task. В HEAD было
   правильно, это сделало изменение в рабочем дереве. Верни типизированный результат с двумя
   исходами (200 и 404) вместо приведения к `(object?)`.
2. **`PriceChangeRepository` не зарегистрирован в DI.** Зарегистрирован только `ProductRepository`.
   Первый же вызов эндпоинта цены упадёт с ошибкой разрешения сервиса.
3. **Неверный маршрут цены.** Он должен быть вложен в товар (`/products/{id}/prices`), а id товара
   надо брать из маршрута, а не из тела запроса. Иначе URL и тело могут расходиться.
4. **Эндпоинт возвращает «сырой» `Result<Guid>`.** Он сериализуется как 200 с собственными полями
   Result. Замапь: успех → 201 с Location, NotFound → 404, Conflict → 409.
5. **`DateTimeOffset.UtcNow` в репозитории.** CLAUDE.md требует `TimeProvider`. Зарегистрируй и
   внедряй его, чтобы тесты управляли часами.
6. **У `GetAllAsync` нет ORDER BY и нет лимита.** Без ORDER BY порядок строк не гарантирован.
   Метод заменит постраничный запрос (задача 6).
7. **У `Result<T>` публичные сеттеры.** Сделай его неизменяемым.
8. **Инициализатор `BaseModel.Id` срабатывает для каждой строки, которую материализует Dapper.**
   Генерируется новый UUIDv7 и тут же затирается. Реши осознанно: принять или генерировать id
   только при создании.
9. **Seed использует `gen_random_uuid()`**, то есть id v4, что противоречит решению про UUIDv7.
10. **Именование:** у `ChangePrice` нет суффикса `Async`.

## Часть 3. Шпаргалка по методам Dapper

| Метод | Когда использовать | Ловушка |
|---|---|---|
| `QuerySingleOrDefaultAsync<T>` | 0 или 1 строка, например поиск по первичному ключу | Бросает исключение при 2+ строках — это правильное поведение |
| `QueryFirstOrDefaultAsync<T>` | Ты намеренно берёшь первую строку | Скрывает дубли; пусть результат ограничивает сама БД |
| `QueryAsync<T>` | N строк, по умолчанию буферизуется | Для огромных потоков используй небуферизованный вариант |
| `ExecuteAsync` | INSERT / UPDATE / DELETE | Возвращает число затронутых строк; 0 значит «не найдено» |
| `ExecuteScalarAsync<T>` | Одно значение (count, exists, возвращённая колонка) | `null`, если строки нет |
| `QueryMultipleAsync` | Несколько результирующих наборов за один round trip | Читать наборы строго по порядку |
| Multi-mapping с `splitOn` | JOIN во вложенные объекты | Неверная колонка разделения даёт тихие null |
| Разворачивание списка в параметрах | Небольшие списки | Текст SQL меняется с длиной списка; с Npgsql лучше параметры-массивы |
| `ExecuteAsync` с коллекцией | Выглядит как bulk insert | Это цикл из N round trip'ов, а не пакетная вставка |

`CancellationToken` всегда передавай через `CommandDefinition`. В транзакции передавай
`transaction` в каждый `CommandDefinition` тоже.

## Часть 4. Задачи по эндпоинтам

### Базовые

**1. GET /products/{id}**
- Цель: вернуть один товар (id, name) или 404.
- Dapper: вариант single-or-default. Id — первичный ключ, поэтому «больше одной строки» — это
  баг, и исключение здесь уместно.
- Проверь: сначала исправь пропущенный `await` (Часть 1, пункт 1).

**2. POST /products**
- Цель: вставить товар с id, сгенерированным в приложении; ответить 201 с Location.
- Dapper: execute (результирующий набор не нужен).
- Валидация: имя не пустое, разумная максимальная длина.

**3. POST /products/{id}/prices**
- Цель: вставить изменение цены товара на заданный момент; по умолчанию «сейчас» из `TimeProvider`.
- Ошибки: нарушение внешнего ключа (`23503`) значит «товара нет», 404. Нарушение уникальности
  (`23505`) значит «цена на этот момент уже есть», 409.
- Улучшение: при перехвате нарушения уникальности проверяй ещё и имя ограничения, чтобы второе
  unique-ограничение в будущем не выдавалось за этот конфликт.
- Валидация: цена > 0, дата корректна, `DateTimeOffset` приведён к UTC перед записью (Npgsql
  отказывается писать ненулевое смещение в `timestamptz`).

**4. GET /products/{id}/price?at= (главный запрос)**
- Цель: цена, действующая на момент `at` (по умолчанию сейчас). Это последнее изменение, начало
  которого не позже `at`.
- Вариант A: запрос только к price_changes, сортировка по началу действия по убыванию, взять одну
  строку. В плане ожидай index scan без шага сортировки.
- Проблема варианта A: `null` двусмысленный. Товара может не быть, а может быть, но без цены
  (Монитор).
- Вариант B (рекомендую попробовать): начать с таблицы products и подцепить одну последнюю цену
  через lateral join. Один round trip различает случаи: нет строки — товара нет (404), строка с
  пустой ценой — на эту дату цены нет.
- Тестируй: Клавиатура до даты первого изменения и точно в эту дату; Наушники с датой в будущем;
  Монитор.

**5. GET /products/{id}/prices**
- Цель: полная история цен, сначала новые.
- Опционально: фильтры `from` / `to`. Если делаешь фильтр необязательным через сравнение
  параметра с null, Postgres может упасть с «could not determine data type of parameter». Приведи
  параметр к типу явно.
- Проверь: это первое место, где ты читаешь `DateTimeOffset` из базы. Напиши тест, который
  подтверждает, что значение читается корректно.

### Пагинация

**6. GET /products?search=&page=&pageSize=**
- Цель: страница товаров, отфильтрованных по подстроке имени без учёта регистра, с общим числом и,
  в идеале, текущей ценой каждого товара.
- Total: используй оконный счётчик по всему отфильтрованному набору, чтобы не делать второй
  запрос. Ловушка: если запрошена страница за концом, строк нет, а значит нет и total. Реши, что
  возвращать (total 0 или отдельный запрос count).
- Порядок: нужен детерминированный порядок с разрешением ничьих (имя, затем id). Offset-пагинация
  без устойчивого порядка даёт дубли и пропуски.
- Текущая цена товара: lateral join, берущий последнюю цену на момент «сейчас». «Сейчас» передавай
  из `TimeProvider`, а не из часов БД, чтобы тесты были детерминированными. Избегай N+1 (по
  запросу цены на каждый товар).
- Безопасность поиска: экранируй `%`, `_` и обратный слэш в пользовательском вводе, прежде чем
  вставлять его в шаблон.
- Индекс: обычный btree не обслуживает поиск по подстроке. Изучи расширение `pg_trgm` и GIN-индекс
  с триграммными операторами. Сравни план до и после.
- Валидация: page >= 1, pageSize ограничен (например, 1–100).

**7. GET /products/feed?after=&limit=**
- Цель: keyset-пагинация, сначала новые, курсор — UUIDv7 id.
- Два текста запроса: один для первой страницы (без условия), другой для следующих (id меньше
  курсора). Избегай универсальной формы «параметр равен null или ...»: она ведёт к худшим планам.
- Бери `limit + 1` строк, чтобы узнать, есть ли следующая страница, и отбрасывай лишнюю. Следующий
  курсор — id последней возвращённой строки.
- Сравнивай uuid только в базе. Postgres сравнивает байты, что совпадает с порядком по времени у
  UUIDv7; сравнение `Guid` в .NET упорядочивает иначе.
- `Guid.CreateVersion7()` упорядочен только до миллисекунды, поэтому строки, созданные в одну
  миллисекунду, приходят в случайном взаимном порядке. Порядок всё равно полный и стабильный,
  поэтому keyset-пагинация остаётся корректной.
- Если позже будешь сортировать по имени, курсор станет парой (имя, id) и потребуется построчное
  сравнение с подходящим составным индексом.
- Докажи это: сними EXPLAIN для первой страницы и для очень глубокого курсора и сравни с offset
  90000 из задачи 6.

### Восстановленные эндпоинты

**8. PUT /products/{id}**
- Цель: переименовать товар, вернуть обновлённую строку или 404.
- Dapper: update, возвращающий изменённую строку, читается через single-or-default. Null значит 404.

**9. DELETE /products/{id}**
- Цель: удалить товар, у которого может быть история цен.
- Заметь: код ошибки внешнего ключа `23503` здесь меняет смысл. При вставке он значит «товара нет»
  (404), при удалении — «на него ещё ссылаются» (409). Будь готов объяснить это на собеседовании.
- Вариант A: один оператор, удаляющий цены и товар вместе (data-modifying CTE).
- Вариант B: два оператора в явной транзакции.
- В обоих случаях: 0 затронутых строк у товара значит 404.

**10. DELETE /products/{id}/prices/{priceId}**
- Цель: удалить одно изменение цены.
- Фильтруй по обоим id, чтобы неверный URL не позволил удалить чужую цену.
- 0 затронутых строк значит 404.

**11. PUT /products/{id}/prices/schedule (твоя явная транзакция)**
- Цель: атомарно заменить все будущие изменения цены товара новым списком.
- Зачем транзакция: это несколько зависимых операторов. Обычная пакетная вставка — один оператор,
  и она уже атомарна, поэтому там транзакция ничего бы не доказывала.
- Шаги: заблокировать строку товара, удалить изменения позже «сейчас», вставить новый список.
  Блокировка строки товара сериализует параллельных редакторов. Это тема для разговора: без
  блокировки две параллельные правки расписания могут перемешаться.
- Массовая вставка: передай массивы (id, даты, цены) и разверни их на стороне сервера вместо цикла
  по одной вставке.
- Путь ошибки: если любая новая дата дублирует существующую, всё должно откатиться. Напиши на это
  тест.
- Будь готов объяснить: что будет, если освободить транзакцию без коммита, и на каком уровне
  изоляции ты работаешь.

**12. GET /products/{id}/prices/stats?from=&to=**
- Цель: число изменений, минимум, максимум и средняя цена за период.
- Заметь: среднее по строкам изменений — это не средневзвешенное по времени. Напиши об этом в
  документации.
- Задача со звёздочкой: средневзвешенное по времени. Вычисли период действия каждой цены по началу
  следующего изменения (оконная функция lead), обрежь его по запрошенному периоду, взвесь по
  длительности и раздели на покрытую длительность. Подумай про время до первой цены и про
  последнюю цену, у которой нет конца.

**13. GET /products/{id}/prices/changes**
- Цель: для каждого изменения вернуть предыдущую цену, абсолютную разницу и разницу в процентах
  (оконная функция lag по времени начала).
- Ловушки: деление на ноль в процентах; у первой строки нет предыдущей цены; если фильтровать по
  дате в том же запросе, теряется предыдущая строка для первого изменения в диапазоне. Сначала
  посчитай окно (подзапрос или CTE), потом фильтруй снаружи.
- Именование окна: попробуй именованное окно (WINDOW), чтобы не повторять одно и то же окно три
  раза.

**14. GET /reports/volatility?from=&to=&minChanges=**
- Цель: по каждому товару за период число изменений, минимум, максимум и размах, только для
  товаров минимум с `minChanges` изменениями, сортировка по размаху.
- Используешь: join, group by, having, агрегаты.
- Ловушка 1: inner join отбрасывает товары без истории (Монитор). Реши, этого ли ты хочешь.
- Ловушка 2: при left join подсчёт всех строк даёт 1 для товара без истории. Считай колонку из
  присоединённой таблицы.
- Заметь: группировки по первичному ключу достаточно, чтобы Postgres разрешил выбирать остальные
  колонки товара.

**15. GET /reports/current-prices**
- Цель: текущая цена каждого товара (классическая задача «последняя строка в группе»).
- Реши тремя способами и сравни планы: distinct-on, row-number в подзапросе, lateral join.
- Ожидание: lateral join выигрывает, когда нужна лишь страница товаров, потому что цены ищутся
  только для них. Остальные два обрабатывают всю таблицу.
- Опиши компромисс в `docs/queries.md`.

**+ GET /health**
- Используй health check для Npgsql. Он должен подтверждать соединение с базой, а не только то,
  что процесс жив.

## Часть 5. Индексы и план EXPLAIN

1. **Существующий индекс.** Unique-ограничение уже даёт btree по (product_id, effective_from).
   Btree можно сканировать в обратном порядке, поэтому «последняя запись до даты» обходится без
   сортировки.
2. **Малые данные обманывают.** На 11 строках Postgres выберет последовательное сканирование.
   Сначала сгенерируй данные: около 100 тысяч товаров с именами вроде «Product N» и около 20
   изменений цены на каждый с шагом 10 дней и случайными ценами. Затем выполни `ANALYZE`.
3. **План «до».** Индекс ограничения нельзя удалить, не удалив само ограничение. Сделай копию
   таблицы цен без индексов и выполни тот же запрос на ней.
4. **Какие планы собрать (все с ANALYZE и BUFFERS):**
   - Задача 4 на таблице с индексом и на копии без индексов.
   - Задача 6 с триграммным индексом и без него.
   - Задача 6 с offset 0 и offset 90000 против задачи 7 при глубоком курсоре.
   - Задача 15 во всех трёх вариантах.
5. **По каждому плану запиши:** тип сканирования, был ли шаг сортировки, сколько строк отброшено
   фильтром, buffers hit против read, время планирования и выполнения.

## Часть 7. Самопроверка к собеседованию

- Почему UUIDv7, а не v4? Почему id генерируется в приложении?
- Почему keyset, а не offset? Чем за это платишь (нельзя перейти на страницу N)?
- Чем удобен `count(*) over()` и когда он вредит?
- Почему для поиска по подстроке нужен триграммный индекс, а не btree?
- Почему код 23503 — это 404 при вставке, но 409 при удалении?
- Где именно нужна твоя транзакция и почему одного оператора там недостаточно?
- От чего защищает блокировка строки товара?
- Чем single отличается от first в Dapper? Почему цикл execute — это не bulk insert?
- Почему left join с простым подсчётом строк даёт неверный результат?
- Три способа получить последнюю строку в группе и когда выигрывает каждый.
